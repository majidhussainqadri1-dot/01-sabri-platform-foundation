# File 01 V12.3 — fail-closed optional companion manifest integrity

**Date:** 2026-11-16. **Requirement:** `F01-FR-003` dependency resolver, in conjunction with `F01-CEN-03` fail-closed activation. Repository-source candidate only; never a live incident claim.

## Confirmed root cause

`SPF_Dependency_Resolver::walk()` already denies a required owner with `manifest_valid=false`. However `optional_status()` checked only a matching version range and registered/compatible/active state. Thus a persisted companion with corrupt `manifest_json` could be returned as `optional_available`, misleading consumers that depend on optional readiness.

## Reproducible red CI

The added disposable WordPress/MySQL test registers a synthetic File 20 with a valid manifest, confirms optional availability, corrupts its stored manifest JSON, then expects `optional_manifest_invalid` and `available=false`. It deletes the synthetic module in `finally`. No live/staging database is used. Test-only HEAD: `b4075fa8612f5ccbe68d69c7579b8e5aee8b56e9`. GitHub Actions Run **43797778318** failed only in the WordPress/MySQL runtime job, with the exact intended assertion `F01-FR-003: malformed optional owner manifest was advertised as available.` PHP 8.1 and 8.3 source QA succeeded.

## Bounded source correction

The optional dependency branch now checks the persisted module DTO's `manifest_valid` before treating the target as available. Invalid manifests return `available=false`, `code=optional_manifest_invalid`, preserving declared `fail_mode`. File 01's core `ready` does not become false only because an optional dependency failed. No schema/permission/contract bump or companion write.
