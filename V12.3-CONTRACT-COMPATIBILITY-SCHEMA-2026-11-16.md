# F01-FUT-007 — Contract compatibility requires trustworthy schema inputs

**Date:** 16 November 2026. **Source scope:** File 01-B / V12.3 Draft PR #14; no deployed system or companion repository changed.

## Root cause and reproduced red test

`SPF_Platform_Engineering::contract_compatibility()` cast `$old['schema'] ?? []` and `$new['schema'] ?? []` to arrays, silently treating absent and scalar malformed schemas as empty contract field sets. With valid monotonically increasing SemVer, it could return `compatible=true` despite insufficient evidence about the old or new API contract.

At **test-only commit** `d7cd1e55c74180ee9d2275c4d9033aab846c9b53`, two precise negative assertions were added. GitHub Actions run `43803986341` source jobs on PHP 8.1 and PHP 8.3 both failed with:
- `F01-FUT-007: missing old/new contract schema falsely passed compatibility.`
- `F01-FUT-007: scalar contract schema was silently coerced and accepted.`

## Limited code correction

The compatibility analyst records a **breaking** `contract_schema_missing` finding if either old or new schema key is absent; it records **breaking** `contract_schema_invalid` if any supplied schema is not an array. Structural comparisons continue using arrays but can no longer certify a malformed input. Deliberately explicit `schema: []` is allowed for a legitimately field-free contract. Existing field removal, type change, new-required-field, major-bump and version-regression rules remain unchanged.

The result still supports pure analysis only: no contract mutation, no automatic approval, no File00 bypass, no deployment, no database migration and no new API. Final exact-head CI, owner contract provenance, real consumer adapters, independent review and staging/live evidence remain separate release gates.
