# F01-FUT-010 — release train fail-closed declaration repair (16 November 2026)

**Scope:** File 01-B, original Master Plan V12.3, "Unified Cross-File Release Train Orchestrator"; plan-only tool, no real deployment. Draft PR #14; independent review and staging/live acceptance remain outstanding.

## Proven defect

`SPF_Platform_Engineering::plan_release_train()` previously iterated over `(array)($manifest['required']??array())`. A missing `required` field became an empty dependency list and a scalar value `'file-01'` became a one-element list. Both could produce `valid=true` without an owner-approved array declaration. An absence of a dependency claim must not become positive proof of zero dependencies.

Two deliberately failing assertions were added to `tests/future-foundation-tests.php` at exact red commit `fcde5b0ab645665b6ce5d49ff46b9a51937cee0c`. GitHub Actions run `43802909503` failed in PHP 8.1 and 8.3 jobs with the exact two asserted failures:
- `F01-FUT-010: missing required dependency declaration accepted as empty.`
- `F01-FUT-010: scalar required dependency declaration silently coerced to array.`

## Bounded correction

The planner now requires the explicit `required` key and an array before reading a module's SemVer and dependencies. Missing and scalar fields produce `required_dependencies_missing` and `required_dependencies_invalid` respectively in `manifest_errors` and ensure `valid=false`. A deliberately empty `required: []` remains valid; no owner manifest is fabricated. Existing duplicate/module-key/semver and cycle checks remain in force.

**Caveat:** This is a source-only coding fix. The actual File00–26 owner manifests and real dependencies still require independent approvals. No File 00/02/20/24/25/26 repository, Hostinger, WordPress staging/live data, database table, release authority, or plugin package version was changed in this correction.
